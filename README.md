# RouteAhead — Android app

Turn-by-turn navigation that drives a handlebar-mounted ESP32 display over BLE, so you
don't have to look at your phone while riding.

Companion firmware: [ESP32_RouteAhead](https://github.com/H2kM33t/ESP32_RouteAhead)

## What it does

- Search for a destination by name, or drop a pin on a map
- Fetches a route with real turn-by-turn instructions (OSRM)
- Follows your GPS, snaps you to the route, and counts down to the next turn
- Streams the turn, distance, speed, ETA, remaining distance, street name and a
  heading-up map of the road ahead to the device once a second
- Sends map *context* with it — the roads branching off the route and the places beside
  it — so the handlebar display shows a junction rather than a line in the dark
- Reroutes automatically if you leave the route
- Keeps running with the screen off, via a foreground service

Everything is free and key-less: OSRM for routing, Nominatim for search, Overpass for
map context, OpenStreetMap tiles for the picker.

## Map context

The side roads and landmarks are fetched from Overpass **once per route**, cached for
the trip, and re-projected into the bike's frame on every GPS fix. Two reasons it works
that way:

- Overpass runs on shared public instances. Querying it at 1 Hz would be both rude and
  far too slow to keep up with a display that redraws twenty times a second.
- The per-fix work is then pure arithmetic — project, filter to what's within 280 m
  ahead, keep the nearest few — which is cheap enough to run on every fix without
  touching the network at all.

It is deliberately fire-and-forget. Navigation starts the instant the route arrives and
never waits on Overpass; if it is slow or down the rider gets a bare route line, which is
exactly what they had before, and the context appears a few seconds later or not at all.

Side roads are found by asking Overpass for road geometry in a 120 m corridor and then
picking the junctions out locally — Overpass can't express "within 30 m of this
polyline". Arms running within 25° of the route are discarded, because those are the
route's own road coming back under a different OSM way id.

## Building

Open in Android Studio and hit Run, or from the command line:

```bash
./gradlew assembleDebug
```

The APK lands in `app/build/outputs/apk/debug/app-debug.apk`.

Run the unit tests — they need no device or emulator:

```bash
./gradlew testDebugUnitTest
```

## Architecture

```
ui/          Compose screens + ViewModel
nav/         NavigationController (the session), snapping, foreground service
routing/     OSRM routing, Nominatim search, geodesy
protocol/    The binary frame sent to the ESP32
ble/         GATT client: scan, MTU, write queue, auto-reconnect
```

`NavigationController` is a process-wide singleton held by `RouteAheadApplication`, not
a ViewModel. A ride lasts longer than any Activity, and the phone spends most of it in a
pocket with the screen off, so the session has to outlive the UI.

## The wire protocol

`protocol/NavPacket.kt` and the firmware's `BleManager::parsePacket` are two halves of
one contract. **Change one and you must change the other.**

| Bytes | Meaning |
|-------|---------|
| 0     | protocol version (currently 4) |
| 1     | flags: bit0 hasRoute, bit1 offRoute, bit2 arrived, bit3 rerouting |
| 2     | maneuver ordinal (`Maneuver` enum) |
| 3–4   | uint16 distance to the maneuver, metres |
| 5–6   | uint16 speed, 0.1 km/h units |
| 7–8   | uint16 ETA, seconds |
| 9–10  | uint16 remaining distance, decametres |
| 11    | number of route points (0–20) |
| 12…   | per point: int16 x, int16 y — centimetres, bike-relative, +Y ahead, +X right |
| then  | uint8 landmark count (0–5) |
| then  | per landmark: int16 x, int16 y, uint8 type (`Landmark.Type` ordinal) |
| then  | uint8 branch count (0–6) |
| then  | per branch: int16 x, int16 y, uint8 heading ÷2°, uint8 length ÷2 m |
| then  | uint8 street name length, then that many UTF-8 bytes (max 22) |

All little-endian. Worst case **178 bytes**, against the 182 usable at the MTU of 185 the
client negotiates. Every variable-length block is length-prefixed and appears in a fixed
order, so the firmware can validate a whole frame before it touches its display state.

Branch headings are relative to the direction of travel (0 = straight ahead, clockwise),
not compass bearings — the device draws everything heading-up and knows nothing about
north.

Three rules that are easy to get wrong:

1. **The `Maneuver` and `Landmark.Type` enum orders are frozen.** Both travel as raw
   ordinals. Append new values at the end only — inserting one in the middle silently
   shows riders the wrong arrow, or a hospital cross on a petrol station. `NavPacketTest`
   fails if an ordinal moves.
2. **The MTU must be negotiated.** The default ATT MTU is 23 bytes, leaving 20 for the
   payload; a full frame is up to 178. `BleRouteClient` requests 185 and doesn't report
   Connected until the stack answers.
3. **Identical frames still have to be resent.** The device treats six seconds of silence
   as a dropped phone. At a standstill nothing changes, so `NavigationController`
   heartbeats the last frame every 3 s — without it the device flapped in and out of
   "No signal" while perfectly connected.

`NavPacketTest` mirrors the firmware's parser line for line, so a layout change on one
side alone fails the build rather than showing a rider a wrong turn on the road.

## Permissions

| Permission | Why |
|---|---|
| `ACCESS_FINE_LOCATION` | following the route |
| `BLUETOOTH_SCAN` / `BLUETOOTH_CONNECT` | talking to the device (API 31+) |
| `FOREGROUND_SERVICE_LOCATION` | staying alive with the screen off |
| `POST_NOTIFICATIONS` | the ongoing navigation notification (optional) |
| `INTERNET` | routing and search |

## Known limits

- The public OSRM demo server has no uptime guarantee and rate-limits. Self-host or
  swap `OsrmClient.BASE_URL` before this goes near real users.
- Nominatim allows 1 request/second; search is debounced by 400 ms to respect that.
- No offline routing — a route needs a connection to fetch, though following an already
  fetched route works fine without one.
- The `driving` profile is used, as the closest match to a motorbike on public roads.
  `OsrmClient.Profile` also has `CYCLING` and `WALKING` if you want them exposed in the UI.
